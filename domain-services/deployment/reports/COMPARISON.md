## Analysis

Written by hand for task T120 from the observations files (`baseline/observations-*.json`,
`redesign/observations-*.json`). Figures are per run: end of run minus start for counters, the mean
of the 5-second samples for gauges, and the measurement window only for MySQL statement digests.
The three runs of each profile agree to within a few percent, so one representative value or range
is given. The redesign runs measured commit `a2d5da8`; the Phase 8 changes are only scripts,
reports and a comment in the compose file, so no service code differs from that commit.

### Result in one paragraph

The redesign **meets** the scan and start p95 targets by a wide margin and **misses** the
throughput and complete p95 targets by a wide margin. All four results have one cause. Under
stress, completion is now limited by **row-lock queuing on hot SKUs in Inventory**, which each
completion goes through twice (reserve, then commit). Completion went from 357 ms to 1,953 ms at
p95. The load client is closed-loop: each station waits for its completion before starting a new
basket. So slower completions mean fewer transactions, fewer scans per second and a lighter load on
Checkout, and part of the scan and start improvement comes from that lighter load.

### Per SC-009 metric

**Scan p95: MET (69.0 ms against at most 266.0 ms; baseline 295.5 ms).**
- *What changed:* in the baseline, about 54 of Checkout's about 118 ms per scan was waiting for one
  of 10 connections. Completion's `fulfill_checkout` call ran on those same connections and spent
  18.6 ms each under row locks (28.6% of all statement time). In the redesign, completion's
  stock work runs on Inventory's own connections, a scan uses one local transaction with a local
  price read, and Checkout's mean acquire time is about 3 ms.
- *Load caveat:* Checkout served about 1,090 requests/s against about 1,614 in the baseline, because
  stations spent most of their time waiting on completion. At that load its pool was already
  about 80% busy (mean active 7.7–8.2 of 10). At the baseline's request rate the pool would be at or
  over capacity, so these runs do **not** show that the scan improvement would hold at equal
  throughput. Part of the gain is the lighter offered load, not the architecture.
- *Defects:* F1 cannot account for the gain: the baseline's analytics no-op statements were 0.3% of
  stress statement time. F9 is ruled out: both topologies ran a Checkout pool of 10. F7 (the shared
  instance) is not supported as a cause: MySQL used about 3 of 24 cores, and the redesign's private
  checkout-db commits are slower (3.7 ms against 2.9 ms), not faster. F5 is ruled out: the baseline
  had no errors, so no 4xx was masked as a 500. F12 works *against* the redesign here. The scan-only
  gateway-minus-Checkout gap of about 42 ms persists under stress in the redesign (about 2.3 ms in
  the baseline), so without it the redesign's scan p95 would be lower still. Its cause under stress
  is not established by these observations. The F12 row above is corrected accordingly.
- *Attribution:* the gain comes from moving completion's locking work off Checkout's connections
  (the saga, F6) and from the single-transaction local scan path, both parts of the redesign, plus
  the lighter offered load described above.

**Start p95: MET (49.0 ms against at most 304.1 ms).** In the baseline, start waited in the same
saturated Checkout pool (about 120 ms of server time). In the redesign, Checkout's start server time
is 9–10 ms. The same load caveat applies. The redesign's `INSERT INTO checkout_transactions` averages
3.6 ms, mostly its commit. No defect in the table accounts for the difference: F12 affects starts
equally in both topologies under stress, where it is small.

**Successful scan throughput: UNMET (912.7 scans/s against at least 1,355.1).**
- *Likely cause:* slower completions in a closed-loop workload. The time per basket per station
  explains the throughput:
  - baseline: 10.5 scans × about 120 ms, plus a start of about 120 ms and a completion of about
    150 ms, gives about 1.53 s per basket;
  - redesign: 10.5 × about 54 ms, plus about 10 ms and about 1,700 ms, gives about 2.28 s per basket.
  - 200 stations × 180 s divided by those times gives about 23,500 and 15,800 baskets, the measured
    transaction counts.
- Basket size is unchanged, so scans per second fall in proportion.
- *Defects:* none in the table accounts for it. F1–F5 and F12 have no throughput effect here, and
  F9 is equal in both. The loss comes from the completion design (F6) under hot-SKU contention.

**Complete p95: UNMET (1,953.3 ms against at most 356.5 ms).**
- *Likely cause:* each completion makes two Inventory transactions, reserve and commit. Each one
  locks every basket SKU with `SELECT … ORDER BY sku FOR UPDATE` and holds the locks through its
  own redo-log flush.
  - The load client's Zipf SKU choice puts the same few SKUs in almost every basket, so those
    transactions queue on the hot rows: 48.6 ms mean lock wait per statement and about 1,505 s of
    lock waiting per run, against about 406 s in the baseline's one locking call per completion.
  - Because the lock queue is long, all 10 Inventory connections are almost always held, and about
    130 more requests wait for a connection (mean acquire time about 760 ms, paid on each of the two
    calls).
  - The sum, roughly 2 × (760 ms + 49 ms + about 3 ms) plus Checkout's own steps, matches Checkout's
    measured 1.7 s per completion.
  - When an Inventory call waits longer than Checkout's 1.5 s read timeout, the completion answers
    the documented `503 SERVICE_UNAVAILABLE`. That accounts for the 10 stress errors (5, 2 and 3 per
    run, all `COMPLETE_TRANSACTION`). The recovery worker resolved every one of them: R-3 and R-5
    pass in every reconciliation.
- *Normal load:* complete p95 also rose, from 15.0 ms to 55.8 ms, with no contention (Inventory pool
  idle, about 0.5 ms locking reads). The saga's fixed cost explains part of it: up to about 2.9 Checkout
  commits per completion (an upper bound, because the count also includes the outbox relay's own
  commits) and about 1.8 Inventory commits, at about 2 ms each at normal load, plus two Inventory
  HTTP calls. Checkout's complete server time is 37–38 ms against 7.9 ms. These observations do not
  break down the rest.
- *Defects:* F6 is the architectural change under test, and these differences are attributed to it,
  as the table says. No other defect applies: F9 is equal, F5 does not apply (0 baseline errors),
  and F1–F4 and F12 do not touch completion.

### Corrections to the defects table

- **F12:** the original *Effect* text said the stall does not affect the SC-009 stress targets.
  That holds for the baseline, but in the redesign a scan-only gap of about 42 ms persists under
  stress. The row now says so. The correction is in `compare-reports.sh`, so it survives
  regeneration.
- **F9:** the pool sizes turned out equal (both 10, see `redesign/POOL-SIZING.md`), so F9 has no
  effect on these runs. The deadlock-retry part still differs: the baseline had 77–85 scan retries
  per stress run, and the redesign had none because its scan path no longer deadlocks.
- The F1–F6 rows are consistent with the observations.

### What would address the unmet targets (not done; outside Phase 8)

These are hypotheses for follow-up work, not measured results:
- Shorten how long Inventory holds hot-row locks.
- Avoid locking every basket row twice per completion, for example by doing the commit step as
  conditional single-row updates without the `FOR UPDATE` read.
- Re-measure.

Raising Inventory's pool size is not expected to help: it would move the queue from Hikari into
InnoDB lock waits.
